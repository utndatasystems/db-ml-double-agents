## A8-1: restored supporting DOI cache is ignored by offline evidence reuse

Severity **medium**, confidence **high**. Diagnosis and final implementation/test review **approved by specialist 9**, including an independent 28-test cache/coverage run. Concurrent cache writers remain uninspected.

- References: `scripts/refresh_affiliations.py:49` builds inputs from ER and canonical publication fingerprints only; `:51`-`:57` returns immediately on matching policy/inputs, before opening supporting cache at `:65`; `:85` atomically installs a newly built evidence snapshot. `scripts/automatic_affiliations.py:113` returns no metadata for an offline cache miss; `:234` records `metadata_unavailable`.
- Trigger: run offline with a missing DOI cache row, then restore/populate that cache without changing identity or publication input bytes. Intended behavior is that newly available local supporting evidence can be consumed by an offline refresh.
- Expected: second offline run matches the restored exact-name, title, DOI and dated author metadata. Actual: second run reuses the first incomplete snapshot and still reports no candidate. Removing only the output snapshot and running the same inputs yields one valid candidate from `Recovered University`.
- Impact in boundary fixture: 0 -> expected 1 author-specific candidate; ordinary retry remains 0. No identity, classification or threshold change is needed to reproduce.
- Actual stored data: snapshot contains 1,126 people, 775 with candidate evidence, 2,275 candidate rows and 3,896 checks. 517 checks are `metadata_unavailable`; 289 checked DOI URLs have no row in the current supporting SQLite. None of the previously unavailable checks currently has a positive SQLite response, so **no currently lost recovered candidate is demonstrated**. These missing rows establish operational exposure, not proven wrong affiliation selections.
- Fix options: track semantic/fingerprinted supporting-cache state on generated snapshot and require equality to reuse; or rebuild offline snapshots when local cached evidence changes. Preserve ability to reuse a validated complete existing snapshot when the supporting cache is entirely absent. Do not indiscriminately rebuild from an absent cache and destroy retained evidence. Existing snapshots need a migration/rebuild rule; byte fingerprints require thought about SQLite WAL, whereas hashing response records or selected response tuples avoids that concern. Evidence parser changes also need a version/fingerprint invalidator.
- Risks: additional local CPU and cache fingerprint I/O; careless migration can discard previously complete evidence. Cache removal and cache recovery differ and need explicit cases.

Implemented: `metadata_cache_fingerprint()` at `scripts/refresh_affiliations.py:19` streams ordered committed response tuples through read-only SQLite, including committed WAL; hash version/tag stored separately as top-level `metadataCache` (`:101`) to retain the primary-input shape used by the builder. Offline reuse at `:76` requires equal supporting fingerprint when the cache exists. Matching primary inputs/policy with an entirely missing cache preserves the prior output without creating an empty supporting database. Legacy snapshots rebuild when a cache exists and remain reusable when it is absent. `POLICY_VERSION` retains its evidence-code invalidation role. A present but partially restored cache is evaluated according to the existing method using its available rows; no new carryover semantics were introduced. Thus restoring a partial cache can remove previously retained evidence whose response rows are absent; explicit cached 404 responses also invalidate positives as intended.

Same-input executable comparison: `.venv\Scripts\python.exe data\reports\round2\pipeline_fix_verification.py` loads the unchanged `HEAD` implementation into a temporary in-memory module and exercises the identical real entry-point/cache fixture against baseline and fixed code. Recorded in `pipeline_fix_verification.json`: baseline ordinary retry 0 candidates vs forced rebuild 1; fixed ordinary retry 1 vs forced rebuild 1. Actual production recovered-candidate impact remains **0 demonstrated** until root's controlled refresh.

## A8-2: interrupted browser export exposes a manifest before its new assets exist

Severity **medium**, confidence **high**. Raised by specialist 9; investigated here. Specialist 9 approved the narrow ordering/atomicity diagnosis; root implemented the shared-file fix.

- References in current working file: `scripts/build_site_data.py:2575` replaces full JSON; `:2583` writes browser JS; `:2586`-`:2587` subsequently create detail/search files. `write_browser_detail_files()` at `:2399` removes obsolete content-hashed detail JSON before writing replacements; `write_browser_search_file()` at `:2415` similarly removes old search assets first. Line numbers can shift during other authorized edits.
- Trigger: a correction changes a deferred publication title and thus its asset hash; process interruption/disk-full after the new `site_data.js` is installed or during detail creation. Intended rule: a visible manifest should reference complete artifacts.
- Expected: a failed export leaves the previous usable manifest/assets, or installs a new manifest only once all assets exist. Actual: the new manifest references a missing detail JSON and missing search JSON. Injecting disk-full at the next temporary detail write additionally removes the old detail asset before the failure.
- Boundary fixture: real browser payload/writers, one changed deferred paper; two referenced assets missing at the first failure boundary; zero detail assets left after failure. A successful retry repairs both, so this is interrupted-generation availability/inconsistency, **not inability to recover after a completed retry**.
- Actual stored data: specialist 9's reconciliation found current manifest assets present. No current production interrupted export is alleged. Any future changed detail/search hash is exposed at this ordering boundary.
- Proposed fix: materialize new immutable content-hashed assets without deleting old assets, atomically install `site_data.js` after those writes succeed, then garbage collect obsolete files. Consider readers that already hold an old manifest: immediate old-asset removal can still break those active browser sessions. Retaining a bounded previous generation is a possible scope extension; full transactional consistency across JS/full JSON/home/coverage is broader and should not be claimed by a narrow ordering fix.
- Risks: orphan assets following failure, bounded extra disk usage, and preservation/cleanup policy. The website design need not change.

Implemented by root: `write_browser_export()` at `scripts/build_site_data.py:2422` stages detail/search assets atomically before replacing the browser JS. The main entry point calls it after other report/export work; there is no claim of a transaction spanning all exported files. Cleanup keeps current plus immediately preceding distinct asset-generation references, including additional explorer people; repeated identical asset generations retain prior files. Unreadable legacy manifests disable pruning conservatively. Older open tabs beyond that retained generation are still outside this bounded guarantee.

Regression coverage in `tests/test_build_site_data.py:41` injects failures at detail, search and browser-JS promotion and verifies old JS/reference survival; successful retry checks both generations; repeated v2 retains v1, distinct v3 prunes v1; malformed previous JS preserves unknown old references. Initial repeat-v2 test exposed a cleanup idempotence gap in the first patch, which root fixed before final validation.
