## A3.1: deleted review entries remain applied on direct invocation

Severity medium, confidence high; current wrong identities not established. `scripts/apply_profile_entity_resolution.py:174-210` consults current reviews only. Deleting an applied row sends the group through the general rule, which rejects an already-reviewed status as `not_sparse_exact_assignment` (`:133-135`). Deleted aliases also never enter `plan_alias` (`:234-236`). Existing reviewed PID and review-added candidate links survive indefinitely under direct `apply_profile_entity_resolution.py --apply`. This conflicts with the reviewed-decision scope and the explicit persistent-decision deletion requirement. The normal `run_pipeline.py:706-748` reindex resets base decisions first and therefore limits this failure to direct/manual stage usage.

Fixture: apply a Ken Ross alias, remove its review from `build_plan` inputs; actual plan is empty and the status stays `resolved_reviewed_service_alias/full`. Expected: defer the module-owned unsupported assignment, clear its reviewed candidate link, preserve genuine DBLP candidates and unrelated automatic decisions, propagate the final cleared anchor to dependent aliases. Production counterfactual removes all review inputs without touching DB: all 17 reviewed assignments receive no clearing proposal. This measures exposed assignments, not 17 current errors. Current inputs have zero missing entries. A3.1 was independently confirmed by specialist 2, who challenged normal-pipeline impact and missing-whole-file semantics.

Proposed narrow fix: detect only owned reviewed statuses with a missing corresponding review; defer rather than restore the original PID; preserve unrelated resolutions; recompute alias dependencies and delete only review-added candidate links. Tests should cover single/all deleted rows, retained dependent aliases, unrelated statuses, and repeated execution. Accidental omission of an entire CSV would conservatively defer its decisions; report that scope rather than silently preserve unsupported assignments.

## A3.2: manual affiliation evidence accepts a publication version the person did not author

Severity medium, confidence high on implementation boundary; zero current affected manual evidence rows. `scripts/build_site_data.py:1647-1655` validates reviewed publication membership using all `resolvedVersions`, disregarding `personVersionDblpKeys` preserved by `:1475-1478,:1564-1565`. The intended own-publication constraint is explicit in `data/README.md:155` and the function docstring. `scripts/focus_population.py:201-218` already implements the conservative person-owned component contract. Reviewed affiliation rows establish institution evidence, not reviewed publication authorship; the latter has its separate `reviewed_publication_authors.csv` mechanism.

Fixture: Alice owns only `own-preprint` (2026); the work contains explicitly nonowned `others-conference` (2025). A manual affiliation row referencing that conference passes validation and replaces Own University with Coauthor University. Expected: reject the row as lacking matching person-owned publication evidence. Production scan finds 14 person-work rows with partial component ownership and zero of the four current reviewed affiliation rows referencing an unowned component. Therefore no current affiliation/count change is predicted from this guard alone.

Related, not yet a demonstrated wrong assignment: `automatic_affiliations.publication_dois:38-43` likewise considers same-year unowned component DOIs. Two stored rows expose such extra DOI candidates: PID26/6037 `journals/corr/abs-2103-14699` imports DOI10.1145/3486607.3486750 from `conf/oopsla/BastaniHJBM21`; PID263/2590 `journals/corr/abs-2509-24350` imports DOI10.1007/978-981-95-6196-4_11 from `conf/adc/KeYDCH25`. Proposed fix: validate manually referenced components against explicit person ownership; missing ownership permits only the selected publication, matching F4 compatibility policy; explicit empty ownership permits none. Preserve full component metadata for browsing. Existing test accepting an explicit older merged version must gain explicit ownership if authored; add nonowned/empty/legacy tests. Automatic DOI filtering needs separate analysis of refresh input serialization and policy-version invalidation before changing it.
